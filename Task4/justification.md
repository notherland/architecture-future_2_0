# Обоснование Terraform-конфигурации

## Выбор ресурсов

| Компонент | Ресурс | Параметры | Почему |
|-----------|--------|-----------|--------|
| Network | `yandex_vpc_network` + `subnet` | CIDR `10.10.0.0/24`, зона `ru-central1-a` | Изолированная сеть платформенного домена; достаточно для пилотной VM и сервисов |
| NAT | `yandex_vpc_gateway` (shared egress) + route table `0.0.0.0/0` | Managed NAT | Исходящий интернет для обновлений/агентов без публикации всех внутренних IP; надёжнее NAT-инстанса |
| Security Group | SSH (ограничиваемый CIDR), HTTP, egress any | Минимальный доступ | Базовый периметр ИБ для мед/фин контуров |
| VM | `standard-v3`, 2 vCPU / 4 GB RAM | Пилот app/bastion | Хватает для портала/агента интеграций на старте; дешево масштабировать cores/memory через переменные |
| Boot image | `data.yandex_compute_image` family `ubuntu-2204-lts` | Актуальный image_id | Хардкод ID устаревает (Image not found); family всегда даёт последний образ семейства |
| Boot disk | 20 GB network-SSD | ОС | SSD ускоряет загрузку и системный I/O |
| Data disk | 10 GB network-HDD, secondary | Данные/логи | Отделение данных от ОС: проще бэкап и увеличение размера без пересоздания VM; 10 GB укладывается в студенческую квоту network-HDD |
| Публичный IP на VM | `nat = true` на NIC | Админ-доступ | Для пилота; в проде SSH — через bastion/VPN, NAT gateway остаётся для egress |

Вручную (вне Terraform): регистрация облака/каталога, создание SSH-ключей, DNS/сертификаты, секреты в Lockbox — разовые org-шаги.

### Аутентификация провайдера (после 2026-06-01)

OAuth-токен пользователя, выданный после `2026-06-01`, **нельзя** обменять на IAM token — для Terraform нужен **ключ сервисного аккаунта**:

1. Консоль Yandex Cloud → **IAM** → **Сервисные аккаунты** → **Создать**.
2. Назначить на каталог роль `editor` (или минимум `vpc.admin` + `compute.admin`).
3. Открыть SA → **Создать новый ключ** → **Авторизованный ключ** → скачать JSON.
4. Сохранить файл как `Task4/sa-key.json` (в `.gitignore`, не коммитить).
5. В `terraform.tfvars` указать: `service_account_key_file = "sa-key.json"` (+ реальные `yc_cloud_id` / `yc_folder_id`).
6. Применить из `Task4/` с локальным провайдером (registry часто 403):  
   `..\..\.tools\terraform\tofu.exe init -plugin-dir=providers` → `plan` → `apply`.

Опционально: пустой `service_account_key_file` и заполненный `yc_token` — только для старого OAuth/IAM-потока.

## Декларативный подход и IaC

- **Декларативность**: в `.tf` описано желаемое состояние (сеть, NAT, диски, VM и связи), а не скрипт «создай по шагам». Terraform сам строит граф зависимостей (disk → VM, gateway → route → subnet).
- **Воспроизводимость**: те же `main.tf` + `tfvars` поднимают одинаковую среду для Clinic/Fintech/Analytics (смена имён/CIDR через переменные).
- **Масштабируемость**: новые домены — копирование модуля/workspace или `count`/`for_each`; размеры VM/дисков меняются переменными без ручных кликов в консоли.
- **Контроль изменений**: plan перед apply, код в Git/PR — соответствует требованию курса сдавать инфраструктуру через репозиторий.

## Связь с бизнес-целями Future 2.0

Быстрый заказ сред под витрину и домены, единый стандарт сети/ИБ, снижение зависимости от устаревшего железа и ручной сборки — ускоряет time-to-market и подготовку к георезервированию.
